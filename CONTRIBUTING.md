# Contributing to DN DebRIEF

Thanks for your interest in improving DN DebRIEF! This guide covers the basics of contributing to the web platform in [`web/`](web/). By participating, you agree to follow our [Code of Conduct](CODE_OF_CONDUCT.md) and the [AI Contribution Policy](AI_POLICY.md).

## Read the AI policy first

We welcome AI-assisted contributions, but with two non-negotiable rules:

- **Never let an LLM speak for you.** Comments, issues, and pull request descriptions must be written in your own voice.
- **Never let an LLM think for you.** Only submit code you fully understand and can explain.

You may use AI to explore the codebase, draft a function, or write tests, but the final contribution must reflect your own reasoning. Maintainers want to talk to you, not to a model.

## Ways to contribute

- **Report bugs** — open an issue with what you expected, what actually happened, and steps to reproduce (screenshots help for UI issues).
- **Suggest features** — for anything beyond a small fix, open an issue first so the approach can be discussed before you invest time.
- **Fix issues** — browse open issues and leave a comment if you plan to work on one.
- **Improve documentation** — documentation fixes are always welcome.
- **Report security issues** — see [SECURITY.md](SECURITY.md); please do not open a public issue.

## Development setup

You need Node.js 26 and the [Vite+](https://viteplus.dev) (`vp`) CLI. Setup instructions, environment variables, and the full command reference are in [`web/README.md`](web/README.md#getting-started).

```sh
cd web
vp install
vp run dev
```

No external services are required for local development: the database is embedded PGlite, file uploads go to `.data/uploads`, and outgoing emails are logged to the console.

## Project guidelines

### Structure

- Nuxt 4 with three source directories:
  - `web/app/` — client code (pages, components, composables, layouts, middleware).
  - `web/server/` — Nitro server code (API routes, auth, database, server utilities).
  - `web/shared/` — types and pure helpers shared by both, imported as `#shared/*`.
- Never import server code into the client. Put shared logic in `web/shared/`.
- Detailed architecture notes live in [`web/AGENTS.md`](web/AGENTS.md).

### UI

- Prefer Nuxt UI v4 components (`UButton`, `UInput`, `UModal`, ...) and Tailwind CSS v4 utilities over custom one-off styling.
- Use Phosphor icons with the `ph:` prefix, for example `i-ph-plus` or `i-ph-arrow-up-right`.

### Language

- User-facing strings are Slovak.
- Code, comments, database identifiers, documentation, and commit messages are English.

### Database

- Schemas are modularized in `web/server/db/schema/` and use Drizzle ORM, with relations in `relations.ts`.
- After changing a schema, run `vp run db:generate` to create a migration. Do not hand-edit generated SQL that has already been shared or applied.
- In development, migrations run automatically against the embedded database.

### Authentication and authorization

- Authentication is handled by Better-Auth (`web/server/auth/auth.ts`).
- Protect server routes with `requireUser(event, roles)` and client pages with the `auth` middleware plus `allowedRoles` page meta.

## Making changes

1. Fork the repository or create a branch from `main` (for example `fix/registration-deadline`).
2. Write focused commits using [Conventional Commits](https://www.conventionalcommits.org/): `feat:`, `fix:`, `refactor:`, `chore:`, `docs:`, and so on.
   - The changelog is generated from commit messages, so clear, imperative English messages matter.
3. Run the checks before pushing:

   ```sh
   vp run check:fix   # lint, formatting, and type check (required)
   vp run build       # recommended for larger changes
   ```

4. Open a pull request against `main` and describe **what** changed and **why**. Link related issues with `Closes #123` where applicable.

All pull requests touching `web/**` run the `Check` and `Test build` workflows in CI; please make sure they pass. PR descriptions must be written by you, not generated by an LLM, per the [AI policy](AI_POLICY.md).

## Review and releases

- A maintainer will review your pull request and may request changes.
- Releases are cut from `main` via GitHub Releases. Publishing a release builds and pushes the web image to GHCR and deploys it automatically.
